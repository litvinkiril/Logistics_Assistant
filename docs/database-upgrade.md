# База логистики: подготовленная миграция

Миграция: `20261028143308_AddDeliveryPlanningAndBoxTracking`.
Предыдущая: `20261028113952_AddDeliveryOrderBoxes`.

Изменены модели, конфигурация EF Core и snapshot. Старые миграции сохранены.
Миграция не применялась к рабочей базе приложения. Подключаться к ней для создания
миграции не требовалось. Новые таблицы не заменяют существующие данные.

## Как применить в Visual Studio

В консоли диспетчера пакетов выберите проект `Logistics_Assistant`:

```powershell
Get-Migration -Context ApplicationDbContext
Script-Migration -From AddDeliveryOrderBoxes -To AddDeliveryPlanningAndBoxTracking -Context ApplicationDbContext
```

Убедитесь, что предыдущие миграции применены, затем выполните в SQL-редакторе
своей базы `docs/database-preflight.sql`. Ненулевые результаты означают дубли,
несуществующие связанные записи или недопустимые значения. Их нужно разобрать:
миграция не удаляет и не объединяет конфликтующие записи автоматически.

После проверки и резервного копирования базы примените уже созданную миграцию:

```powershell
Update-Database -Migration AddDeliveryPlanningAndBoxTracking -Context ApplicationDbContext
```

Повторно вызывать `Add-Migration` для этих изменений не нужно.
Если таблицы менялись вручную вне EF, сначала сопоставьте реальную структуру
с предыдущей миграцией: `Get-Migration` показывает историю, но не доказывает
отсутствие ручных изменений. Старый SQL из папки с макетами не использовать.

## Связи

```text
products → boxes                            описание упаковки
products → product_units → physical_boxes  конкретные комплекты и коробки

need_to_deliver → delivery_order_needs ← delivery_orders
                       ↓
                delivery_order_units → product_units

delivery_orders → delivery_order_boxes → physical_boxes
                          ↓
                     box_movements
```

### Что добавлено

- `delivery_order_needs`: сколько единиц независимой потребности назначено рейсу,
  сколько доставлено, когда отменён оставшийся план. Отмена не удаляет потребность.
- `product_units`: конкретный экземпляр товара и ожидаемое количество коробок.
- `delivery_order_units`: какие экземпляры зарезервированы для назначения;
  `released_at IS NULL` означает действующий резерв. Уникальный индекс запрещает
  два действующих резерва одного экземпляра. `delivered_at` отмечает фактическую
  доставку; при ней также нужно заполнить `released_at`.
- `box_movements`: погрузка из точки в машину либо выгрузка из машины в точку,
  время, рейс, коробка и пользователь. Из двух полей `from_point_id`/`to_point_id`
  заполнено ровно одно. Рейс определяет вторую сторону перемещения.
- Внешние ключи потребностей, рейсов и коробок, запрещающие ссылки на несуществующие
  записи. Удаление связанных записей ограничено через Restrict.
- Уникальность URL товара (NULL разрешён) и физической коробки, остатка
  `(logistics_points_id, product_id)` и номера упаковки `(product_id, box_number)`.
- `delivery_orders.source_point_id` и необязательные данные машины для черновика.
- `physical_boxes.product_unit_id`, `product_id`, `current_point_id`, `current_order_id`.
  Составные связи запрещают присоединить коробку одного товара к экземпляру другого.
  В комплекте не может быть двух коробок одного типа упаковки.
- `delivery_order_boxes.order_need_id`, `loaded_at`, `unloaded_at`, `cancelled_at`.
  Ваш `DeliveryBoxStatus` сохранён. `point_id` остаётся пунктом назначения.
  У коробки может быть только одно незавершённое, неотменённое назначение.
- Представление `logistics_unit_stock`: полные комплекты в точке, зарезервированные
  и доступные. Комплект целый, если число связанных коробок совпадает с ожидаемым
  и все они находятся в одной точке. Учитываются как резервы комплектов, так и
  активные назначения отдельных коробок.

## Существующие данные

Автоматически заполняется только `physical_boxes.product_id`: он однозначно известен
из `boxes.product_id`. Комплекты, исходная точка рейса, местоположение и времена сканов
не угадываются. Старые записи получают NULL в этих новых полях.

Оба поля местоположения NULL означают «не установлено», а не «на складе».
Потребности с NULL в количестве или назначении сохранены для разбора. Назначать их
рейсу до заполнения нельзя. Старым доставленным коробкам не выдумываются даты сканов.

`warehouse_products` и существующий сервис поиска продолжают читать прежние остатки.
Новое представление пока не подключено к API. До заполнения комплектов оно может
показывать меньше товаров; переключать интерфейс нужно после сверки.

## Что должны делать будущие хендлеры

Это схема хранения, а не реализованная логика погрузки. Для каждой операции:

1. Проверить пользователя, состояние рейса, заполненность машины и исходную точку.
2. При назначении блокировать строку потребности и проверять остаток потребности.
   Учтённое количество: для действующего назначения `quantity`, для отменённого —
   только `delivered_quantity`. Сумма по всем рейсам не должна превышать потребность.
3. Проверять совпадение товара/типа коробки и пункта назначения с потребностью,
   количество выделенных комплектов, их полноту и нахождение в исходной точке.
4. При резервировании коробки и целого комплекта использовать одну стратегию
   блокировки экземпляра товара: отдельные уникальные индексы не предотвращают
   конфликт «один рейс резервирует комплект, другой — одну его коробку».
5. Для скана блокировать назначение/коробку, проверять резерв и местоположение.
   Повторный скан возвращает прежний результат без нового перемещения.
6. Одной транзакцией изменять подтверждение скана, местоположение, журнал и
   выполнение потребности. Счётчик полных товаров увеличивается только после
   приёмки всего экземпляра. Для потребности `box_id` единица — отдельная коробка.
7. Не освобождать резерв загруженной коробки простым заполнением `cancelled_at`:
   сначала оформить реальный возврат или передачу. Снятие резерва комплекта и
   отмена его назначений коробок должны быть согласованы.
8. Ограничить число коробок экземпляра `expected_box_count`, фиксировать состав
   при регистрации. Не менять смысл используемых `boxes` задним числом; версии
   упаковки при необходимости потребуют отдельной модели.

Эти межстрочные правила не заменяются внешними ключами. Их реализация относится
к следующему этапу — сервисам и хендлерам. Числовые положительные значения машины
нужно проверять перед погрузкой; старые нулевые значения здесь не переписываются.

## Откат и тесты

Down допускает откат неиспользованной миграции. Если уже появились комплекты,
назначения, движения, новые данные сканов или черновики с NULL в машине, откат
останавливается до удаления данных. Тогда нужен отдельный план переноса данных.

Интеграционные тесты создают собственные базы `logistics_test_<guid>` на сервере,
указанном в `LOGISTICS_TEST_CONNECTION`, и удаляют только эти базы. Не используйте
для них рабочий сервер. Без переменной эти тесты явно пропускаются; проверки
модели и существующие тесты запускаются обычным `dotnet test`.

Пример для отдельного тестового PostgreSQL:

```powershell
$env:LOGISTICS_TEST_CONNECTION = 'Host=127.0.0.1;Port=55483;Database=postgres;Username=postgres;Pooling=false'
dotnet test Logistics_Assistant.slnx
```
