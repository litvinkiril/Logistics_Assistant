# Упрощённая БД логистики для MVP

Новая миграция: `20261104101802_SimplifyLogisticsMvp`.
Предыдущая: `20261103212709_AddDeliveryOrderResponsibleUser`.
Старые миграции сохранены; для новой базы применяется вся последовательность.

## Восемь таблиц

| Таблица | Данные |
| --- | --- |
| `products` | Модель товара: `id`, `name`, существующий `url` |
| `boxes` | Тип упаковки: `id`, `product_id`, `name`, `quantity_per_product`, размеры, вес, хрупкость |
| `physical_boxes` | Физическая коробка: `id`, `box_id`, уникальный `url`, `current_point_id`, `current_order_item_id`, `status` |
| `warehouse_products` | Существующие товарные остатки: `logistics_points_id`, `product_id`, `quantity` |
| `logistics_points` | Склады и пункты назначения; существующие поля сохранены |
| `delivery_orders` | Рейсы; исходный склад, создатель, ответственный и данные машины сохранены |
| `delivery_order_items` | План рейса: `id`, `order_id`, `box_id`, `destination_point_id`, `quantity` |
| `box_movements` | Журнал: `id`, `physical_box_id`, `order_item_id`, `operation`, `point_id`, `occurred_at`, `user_id` |

Таблицы пользователей ASP.NET Identity сохранены.

Удалены из текущей модели `product_units`, `delivery_order_units`,
`need_to_deliver`, `delivery_order_needs`, `delivery_order_boxes`.
Представление `logistics_unit_stock` также удаляется.
Принадлежность коробок конкретному комплекту товара не учитывается.

## Упаковка и план рейса

`boxes.quantity_per_product` — положительное число одинаковых коробок на один
товар. Например, для шкафа: «Дверь» — 2, «Задняя стенка» — 1, «Крепёж» — 1.
Две физические коробки «Дверь» имеют одинаковый `box_id` и разные `url`.
Названия упаковок уникальны в пределах модели товара.

`delivery_order_items.quantity` измеряется в физических коробках.
Два шкафа для одного пункта назначения означают три строки плана с количеством
4, 2 и 2. План фиксируется при его создании; изменение состава товара не должно
пересчитывать уже согласованный рейс. Строка уникальна по
`(order_id, box_id, destination_point_id)`.

У коробки есть одно текущее назначение `current_order_item_id`; через него
определяются рейс и пункт назначения. Составной внешний ключ также проверяет
совпадение `box_id` коробки и строки плана.

## Местоположение и история

`PhysicalBoxStatus`:

- `0` (`Unknown`) — местоположение не установлено, `current_point_id IS NULL`;
- `1` (`AtPoint`) — коробка находится в указанной точке;
- `2` (`InTransit`) — коробка в машине, точка не задана, назначение строке рейса обязательно.

Коробка в точке может одновременно иметь назначение рейсу: это резерв до погрузки.
Для свободной коробки `current_order_item_id IS NULL`.
`Unknown` не означает наличие на складе; назначение такой коробке не подтверждает погрузку.

`BoxMovementOperation`: `1` (`Load`) — погрузка из `point_id` в машину,
`2` (`Unload`) — выгрузка из машины в `point_id`.
Рейс определяется через `order_item_id`. Журнал сохраняет факты прошлых рейсов,
даже когда текущее назначение коробки изменилось. Внешние ключи запрещают удалить
коробку, строку рейса, точку или пользователя, на которых ссылается журнал.

Остатки API продолжают читать из `warehouse_products`. Миграция не пересчитывает
их по физическим коробкам и не меняет существующие количества.

## Перенос существующих данных

Миграция выполняется одной транзакцией. Перед проверками и переносом блокируется
изменение затрагиваемых таблиц. При ошибке изменения этой миграции откатываются.

- `boxes.box_number` заменяется на `name`: номер 1 становится «Коробка 1».
  `quantity_per_product` получает 1; названия и состав можно уточнить после переноса.
  Размеры, вес и хрупкость сохраняются.
- Прежние назначения коробок группируются в строки рейса по рейсу, типу коробки
  и пункту назначения. Количество равно числу назначенных физических коробок.
- Активные назначения переносятся в `physical_boxes.current_order_item_id`.
  Прежние известные местоположения сохраняются, неизвестные остаются `Unknown`.
- События `box_movements` переносятся с сохранением ID, времени, коробки и пользователя.
  Направление переводится в `operation`, исходная или конечная точка — в `point_id`.
- Физические коробки, их коды, товары, товарные остатки, точки, рейсы и пользователи сохраняются.

Миграция останавливается **до удаления данных**, если есть:

- записи в старых потребностях, распределениях потребностей, комплектах или резервах комплектов;
- отменённые назначения коробок, для которых новая модель не хранит прежние сведения об отмене;
- прежние подтверждения погрузки/доставки без соответствующих событий журнала;
- коробки в машине без действующего назначения тому же рейсу.

Такие записи требуют отдельного согласованного переноса или экспорта. Миграция
не удаляет их автоматически и не придумывает даты сканов, пользователей или местоположения.

## Применение в Visual Studio

В консоли диспетчера пакетов выберите проект `Logistics_Assistant`:

```powershell
Get-Migration -Context ApplicationDbContext
Script-Migration -From AddDeliveryOrderResponsibleUser -To SimplifyLogisticsMvp -Context ApplicationDbContext
```

После просмотра SQL и резервного копирования целевой базы:

```powershell
Update-Database -Migration SimplifyLogisticsMvp -Context ApplicationDbContext
```

`Add-Migration` повторно вызывать не нужно. Для базы на более ранней версии
`Update-Database` сначала применит недостающие предыдущие миграции. Старый файл
`database-preflight.sql` относится к переходу с `AddDeliveryOrderBoxes` на
`AddDeliveryPlanningAndBoxTracking`; проверки упрощения встроены в новую миграцию.

Новая миграция не поддерживает автоматический `Down`: удалённые связи с комплектами
и прежние потребности нельзя восстановить по упрощённой схеме. Возврат к старой
схеме выполняется восстановлением резервной копии. Попытка `Down` останавливается
до изменения таблиц.

## Границы изменения и проверки

Изменены модели, конфигурация EF Core, snapshot, миграция и тесты БД.
Контроллеры, сервисы, интерфейс, обработчики сканирования и автоматическое
изменение товарных остатков не добавлялись.

Будущие обработчики должны одной транзакцией обновлять текущее положение и
журнал, предотвращать повторную запись одного скана, проверять количество по
плану, соответствие коробки строке журнала, исходную точку, назначение и состояние
рейса. Строки плана с историей и типы зарегистрированных коробок нельзя менять
так, чтобы изменился смысл старых событий. Эти правила между записями не заменяются
простыми внешними ключами. `warehouse_products` требует отдельного правила
списания/приёмки многокоробочного товара при реализации операций.

Проверка с отдельным временным кластером PostgreSQL:

```powershell
.\scripts\test-logistics-points.ps1 -AllTests
```

Скрипт создаёт изолированный кластер на свободном порту, запускает тесты и
останавливает его. Проверяются новая база, перенос прежних строк и журнала,
сохранение остатков, ограничения БД и отказ от миграции при непереносимых данных.
Рабочая база приложения для этих тестов не используется.

## Случайные тестовые данные

Откройте `docs/seed-test-data.sql` целиком в SQL-редакторе pgAdmin или DBeaver и
выполните его в базе с применённой `SimplifyLogisticsMvp`. Нужен хотя бы один
существующий пользователь. По умолчанию добавляются 500 товаров, 6 складов,
12 ПВЗ и 100 рейсов; четыре параметра объёма находятся в начале блока `DECLARE`.
Каждый запуск добавляет новый набор и сохраняет существующие записи и пользователей.
Скрипт создаёт упаковки, физические коробки, прямой состав рейсов, историю
погрузки/выгрузки и рассчитывает товарные остатки по полным наборам коробок.
