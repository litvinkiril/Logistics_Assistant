# Проверка складов и ПВЗ

Новые тесты относятся только к справочнику логистических точек и складским
остаткам. Погрузка, выгрузка, рейсы и product_units в эти тесты не входят.

## Один запуск со своей временной PostgreSQL

Откройте терминал в папке решения `C:\Users\1\Desktop\Logistics_Assistant`:

```powershell
.\scripts\test-logistics-points.ps1
```

Скрипт запускает отдельный PostgreSQL на свободном порту локального компьютера,
подставляет тестовое подключение, выполняет 42 проверки и останавливает сервер.
Строка подключения приложения и рабочая БД не меняются. `Update-Database`
для запуска этих тестов выполнять не нужно: миграции применяются только в новых
тестовых базах. Каждый запуск создаёт отдельный каталог в `artifacts/points-tests-*`.
Логи и остановленный кластер остаются в этом каталоге, который исключён из Git.

Если PostgreSQL установлен в другой папке:

```powershell
.\scripts\test-logistics-points.ps1 -PostgresBin 'C:\Program Files\PostgreSQL\17\bin'
```

Нужен PostgreSQL с поддержкой ICU. База тестов создаётся с локалью `ru-RU`, чтобы
проверять поиск русских букв без учёта регистра. У рабочей БД поведение ILIKE
зависит от её локали; её настройки скрипт не меняет.

Для запуска всего решения, включая прежние тесты:

```powershell
.\scripts\test-logistics-points.ps1 -AllTests
```

При проверке 28.10.2026 на PostgreSQL 18 прошли 42 новых теста; полный набор —
60 тестов, без пропусков. Проверены в том числе приложенные SQL-файлы.

## Запуск без автоматического сервера

```powershell
dotnet test Logistics_Assistant.slnx --filter 'Feature=LogisticsPoints'
```

Без `LOGISTICS_TEST_CONNECTION` выполняются проверки входных данных, а тесты с
PostgreSQL явно отмечаются как пропущенные. Это не равнозначно полной проверке.
Можно задать переменную вручную на отдельный тестовый сервер с правом CREATE DATABASE;
фикстура создаёт базы `points_test_<guid>` и удаляет только созданную ею базу.
Запуск скрипта выше предпочтительнее: он не требует выбирать существующий сервер.

## Что проверяется

- Список всех точек и фильтрация `warehouse` / `pvz`.
- Поиск по имени, городу и адресу, русский регистр и пробелы вокруг запроса.
- Литеральный поиск `%`, `_`, `\`; строка с SQL-синтаксисом не меняет запрос.
- Совместная фильтрация по тексту и типу.
- Пустой запрос, отсутствие совпадений, устойчивый порядок одинаковых названий.
- Получение склада и ПВЗ по ID, включая неактивную точку.
- Ответы HTTP 200/400/404, JSON и работоспособность маршрута `/search`.
- Регистрация `LogisticsPointService` и реальная цепочка HTTP → контроллер → EF → PostgreSQL.
- Остатки товара на складе и в ПВЗ, нулевой остаток, товар без остатков и неизвестный товар.
- Запрет дублирования остатка по паре точка/товар, отрицательного количества,
  ссылок на несуществующий товар/точку и удаления точки с остатками.
- Выполнение SQL-проверок и отсутствие сохранённых записей после ROLLBACK.

## Текущее поведение, зафиксированное тестами

В примерах `warehouse` означает склад, `pvz` — ПВЗ. Модель хранит тип строкой и
не содержит enum/справочника. В реальной БД сначала проверьте `SELECT DISTINCT type`.
Фильтр типа обрезает внешние пробелы, но сравнивает регистр точно:
`WAREHOUSE` и `warehouse` — разные значения. Неизвестный тип возвращает `200 []`.
Неактивные точки не скрываются: клиент получает `isActive=false`.

Текущие маршруты:

```text
GET /api/logistics-points
GET /api/logistics-points?type=warehouse
GET /api/logistics-points?type=pvz
GET /api/logistics-points/{id}
GET /api/logistics-points/search?query=Москва&type=pvz
```

Список товаров конкретной точки (`/{id}/products`) пока не реализован — такого
маршрута эти тесты не заявляют. Для проверки её остатков есть SQL. Существующий
поиск наличия товара по точкам сохранён через `SearchProductStockByIdAsync`.

## SQL и ручная проверка

- `logistics-points-check.sql` — только SELECT: типы, точки, поиск, товары выбранной
  точки, сводка остатков, ошибки данных и ограничения. Меняйте значения в CTE `input`.
- `logistics-points-smoke.sql` — создаёт тестовый склад, ПВЗ, товар и остатки,
  проверяет ограничения и завершает ROLLBACK. Запускайте целиком в отдельной сессии.
  Требует последнюю миграцию с уникальностью остатков и проверкой количества.
  При ошибке выполните ROLLBACK и считайте проверку проваленной.
- `logistics-points.http` — ручные HTTP-запросы для Visual Studio/REST Client.
  Адрес взят из текущего HTTPS-профиля проекта; при другом запуске поменяйте baseUrl.
  Ответы зависят от ваших данных; ID 1 замените на существующий ID точки.

Оставшиеся ссылки на удалённый WarehouseStockService заменены на LogisticsPointService.
Метод получения остатков находится в этом сервисе; удалённый файл не восстанавливался.
Позднее обработчики товаров перенесены из Razor Pages в ProductsController:
актуальные маршруты описаны в `controllers-api.md`. Число тестов полного решения
растёт; приведённые выше 60 — результат проверки на этапе добавления тестов точек.

Методика: [интеграционные тесты ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests?view=aspnetcore-10.0),
[перевод ILIKE в Npgsql](https://www.npgsql.org/efcore/mapping/translations.html).
