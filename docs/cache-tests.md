# Примеры тестов HybridCache и Redis

Проверено 04.11.2026: 101 тест прошёл через `test-logistics-points.ps1 -AllTests`
(Redis-проверки в этом запуске пропущены). Отдельно все 4 Redis-проверки прошли
на рабочем контейнере `redis:8` с подключением `localhost:6379` и уникальными
тестовыми префиксами ключей.

В проекте два уровня кэша: локальная память приложения и Redis. Глобальные
настройки — 30 секунд в памяти и 5 минут в Redis. Сервисы товаров и точек
переопределяют их: 1 минута в памяти и 10 минут в Redis.

## Redis приложения в Docker

Из папки решения при запущенном Docker Desktop:

```powershell
docker compose up -d --wait redis
docker compose exec redis redis-cli ping
```

Ожидаемый ответ — `PONG`. Контейнер доступен только на этом компьютере через
`127.0.0.1:6379`; приложение, запущенное из Visual Studio или через `dotnet run`,
использует существующую настройку `ConnectionStrings:Redis = localhost:6379`.
Redis автоматически перезапускается после запуска Docker, если контейнер не был
остановлен вручную. Docker Desktop должен быть запущен перед приложением.
Данные кэша временные: при пересоздании контейнера приложение заполнит его заново.

Остановить рабочий Redis: `docker compose stop redis`.
Тестовый скрипт ниже запускает отдельный контейнер и не останавливает рабочий Redis.

## Запуск тестов

Из папки решения:

```powershell
# Только настоящий Redis: нужен запущенный Docker Desktop.
.\scripts\test-redis.ps1

# Весь набор, включая PostgreSQL, HTTP, поведение кэша и Redis.
# Нужен также локально установленный PostgreSQL (по умолчанию версия 18).
.\scripts\test-redis.ps1 -AllTests

# PostgreSQL и поведение локального кэша без Docker.
# Redis-тесты будут отмечены как пропущенные, если LOGISTICS_TEST_REDIS не задана.
.\scripts\test-logistics-points.ps1 -AllTests
```

Если PostgreSQL установлен в другой папке, передайте
`-PostgresBin 'C:\Program Files\PostgreSQL\17\bin'`.

Redis-скрипт создаёт временный контейнер `redis:7.4-alpine` на свободном порту
`127.0.0.1` и удаляет его после проверки. При первом запуске Docker скачает образ.
Рабочие подключения приложения не используются. Переменные окружения после запуска
восстанавливаются. PostgreSQL-скрипт создаёт отдельный временный кластер и базы.

Обычный `dotnet test Logistics_Assistant.slnx` не требует запущенных серверов:
проверки, которым они нужны, явно пропускаются. Такой запуск не проверяет Redis.

## Что показывают примеры

`CacheBehaviorTests.cs` использует настоящий HybridCache без Redis и настоящую
тестовую PostgreSQL. Перехватчик EF считает SQL-запросы: первый поиск выполняет
запрос, повторный возвращает данные из кэша. Каждый тест получает собственный кэш.

- Товары и точки кэшируются по ID; разные ID не смешиваются.
- URL и фильтры поиска точек обрезают внешние пробелы перед выбором ключа.
- Разные URL, типы точек и поисковые строки используют разные записи.
- Пустые результаты товаров и `null` для отсутствующей точки тоже кэшируются.
- Список точек и пустой поиск используют общую запись.
- `RemoveAsync` заставляет следующий поиск товара снова обратиться к PostgreSQL.
- `RemoveByTagAsync("logistics-points")` сбрасывает детали и списки точек,
  сохраняя кэш товаров.
- Поиск остатков каждый раз читает PostgreSQL: остатки сейчас не кэшируются.

`RedisCacheTests.cs` проверяет настоящий Redis через настройки приложения:

- Второй экземпляр HybridCache с пустой локальной памятью получает товар из Redis.
  Проверяются поля после сериализации, включая кириллицу и URL.
- Удаление ключа удаляет запись и из Redis; новый экземпляр вызывает загрузчик.
- У записей Redis действительно установлен TTL: 5 минут по умолчанию и 10 минут
  при переопределении. Проверяется TTL сервера, без ожидания нескольких минут.

У каждого Redis-теста уникальный префикс `Logistics:tests:<guid>:`. Тесты удаляют
только свои ключи; команды очистки всей базы не используются. В тестах HTTP и БД
Redis отключён, чтобы одинаковые тестовые ID из разных баз не делили кэш.

Для отдельного тестового Redis можно вручную задать `LOGISTICS_TEST_REDIS`,
затем выполнить `dotnet test Logistics_Assistant.slnx --filter 'Feature=Redis'`.
Если переменная задана, недоступность Redis приводит к ошибке, а не к пропуску.

## Ограничения текущего поведения

Автоматического сброса после изменения данных пока нет: приложение сейчас
предоставляет чтение. Если изменить товар или точку напрямую в БД, кэш может
возвращать прежнее значение до истечения срока. Это касается и закэшированного
отсутствия записи. При добавлении операций записи нужно вызывать сброс соответствующих
ключей или тегов после успешного сохранения.

Проверки удаления и тегов выполняются для текущего экземпляра; они не заявляют
немедленную очистку локальной памяти других запущенных приложений. Проверка TTL
не моделирует сбой Redis или истечение локального кэша.

Поведение API кэша описано в
[документации HybridCache](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0).
